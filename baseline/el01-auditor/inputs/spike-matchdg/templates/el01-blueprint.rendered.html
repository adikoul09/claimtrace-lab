ELEVATE 1.0 · EL-01 · Round 0

A claim-level reproducibility auditor

It checks each claim in an ML paper against the paper's own code, and when the two disagree it re-runs the code to measure which difference moves the number. We ran it on a real paper before writing this page.

Paper MatchDG, ICML 2021 Code microsoft/robustdg @ 3eee173 Audited Suppl. Table 11 (MatchDG) · Table 1 (motivating oracle) Runs 542 training runs, CPU only Evidence blueprint page, Evidence section

What the audit found

The paper's method · Suppl. Table 11

MatchDG's own table: nothing refuted, 13 of 28 numbers confirmed within a point

Re-run on fresh MNIST subsets with the rule and a 1-point margin floor hashed first, 13 numbers are Reproduced and 15 are Inconclusive, including every cell at the two hardest rotations (0° and 75°); none is Not reproduced. MatchDG's average is 97.1 against the paper's 97.4, and its gain over ERM reproduces (+3.62 against +3.3). Its edge over RandMatch, +0.3 in the paper, is too small for 3 runs to resolve in either of our runs.

The motivating oracle result · Table 1

The oracle's advantage reproduces, but it depends on how one appendix sentence is read

PerfMatch, which matches on the true stable feature and is not available in practice, beats ERM as the paper says. Read "early stopping based on the validation loss" as cross-entropy and the advantage disappears (−25.8 points, confirmed −25.4 on fresh seeds); read it as the full training objective and it stays.

What works today: the runner and the grader. Repairs, branch patches and the link from each claim to a runnable command were done by hand; claim cards and the settings diff were built by hand and then re-done blind by LLM extractors as a test (see What was automatic).

MatchDG itself: Rotated MNIST with LeNet (Suppl. Table 11)

The one table with the paper's own method that fits a CPU budget: 1,000 images per rotation, six rotations, each held out in turn. Run with the repo's own commands and the three logged repairs only. The paper's Tables 8 and 9 match the code's training settings for this experiment. One data difference does reach it, through MatchDG's checkpoint choice: F7, tested below with no detectable effect.

We ran it twice. The first run's rule, written and hashed before any run finished, used the paper's sd as the margin. Those sds are as small as 0.1 points, so with 3 runs every number came out Inconclusive, even where our mean landed within a tenth of a point. We then set the margin to max(paper's sd, 1 point), but only after seeing that run. So we re-ran the whole table on fresh MNIST subsets and new seeds, with the floor declared and every rule file hashed first, and graded that run alone. The headline quotes the confirmation.

SciCoQA, a benchmark of real paper-code discrepancies, lists two for this repo, both from one ML Reproducibility Challenge report: F1 (row 68) and F7 (row 67). Our hand audit and the blind extraction found F1 and missed F7, so our recall against SciCoQA on this repo is 1 of 2; we added F7 after checking SciCoQA's rows for the repo. F7: SciCoQA's second row reaches MatchDG's checkpoint choice, and does not move Table 11

The data generator saves two copies of every rotated digit: a plain one and an augmented one, made by a random crop and then a random horizontal flip after the rotation (data/data_gen_mnist.py:34-35, 85 at 3eee173). Half the augmented images are mirrored digits that look rotated the other way. The paper never says Rotated MNIST is augmented (the supplement describes augmentation for PACS and Chest X-ray only), and it does not say how MatchDG's first, contrastive phase picks its checkpoint.

Is it on the Table 11 path? For training and testing, no. ERM, RandMatch, the oracle and MatchDG's second phase read only the plain copy (--mnist_aug 0, data/mnist_loader.py:37-40). But MatchDG's first phase validates on pairs of plain and augmented images (reproduce_rmnist_lenet.py:25 → train.py:217-218 → utils/helper.py:173-175 → data/mnist_loader_match_eval.py:38) and keeps the epoch with the best match score on them (algorithms/match_dg.py:263-266). The second phase builds its matches with that checkpoint, so F7 can reach MatchDG's numbers in Table 11, and only those.

The test. Branch h7 removes the flips and keeps every crop: it draws the same random number the flip would. Against the confirmation's data, 108 of 108 plain and label files are byte-identical, and of 21,600 augmented images 10,752 differ only by the flip and none in any other way. MatchDG was re-run on the confirmation's subsets and seeds, paired by run, with the rule hashed before any run: the six-domain average is the primary test, cells are Holm-corrected, and F7 becomes a "setup differs" reason only if its effect survives.

F2 · selection rule

Decisive and ambiguous. Training is identical under all three rules (last-epoch numbers match exactly); only the reported checkpoint changes. Cross-entropy picks epoch 1 at 98% source accuracy; the full objective picks epoch 88 (+4.7, no detectable effect).

F3 · momentum

A training-budget detail, not a failure to train. Under plain SGD every method reaches about 98.5% source accuracy using the spurious feature, and none learns the stable one in 100 epochs (−28.7 for PerfMatch). At 1000 epochs plain SGD matches the code (+0.3).

F4, F5, F6

No detectable effect on the oracle. The ramped weight matters only through F2. DANN and CDANN stay at chance at the paper's learning rate, so their gap is reported as unexplained. Re-tuning λ on source data picks the published λ = 1.0.

F1 · the missing domain (h3)

A "make it run" agent might quietly evaluate on p = 0.9, the nearest domain the code builds. Run as a branch, every number lands near the paper and RandMatch reaches 59.4 against 59.5. Two other changes also bring RandMatch near 59.5, so we report an open question, not a cause.

Verdict rules

VerdictAbsolute claimRelative claim ("A beats B by g")
Reproduced90% CI of (ours − paper) inside ± margin; margin = max(the paper's sd, a practical floor), declared before the runsour paired CI excludes 0 in the claimed direction, and (our gap − paper gap) is consistent with 0, counting both uncertainties
Partially reproducedn/adirection holds, but our gap is significantly larger or smaller than the paper's; a note says which ("gap larger than reported")
Not reproduced95% CI excludes 0 and not equivalentdirection not shown and the gap is significantly smaller
Inconclusiveanything else after the seed budget; the report prints the tightest margin the data supports
Not runnableno number after the execution ladder and allowed repairs; the failing step is shown
Not assessablethe paper does not pin the experiment; the missing details are listed

"Setup differs" is a flag shown next to any verdict, never a verdict of its own. Code sets it when a code omission had to be filled to run the claim, or when a finding's branch has a Holm-surviving effect on a method the claim names; findings that apply but were not tested become notes. The practical floor is a user setting (default 1 accuracy point): the smallest difference a reader would care about. Without it, a paper with sds of 0.1 points (one test image in 1,000) can only ever grade Inconclusive.

Branch effects are paired by seed with 95% CIs, Holm-corrected across the report; the largest is re-run on fresh seeds as a separate test.

The sharpest contrast is with autoarxiv: its agent may run a scaled-down reproduction (a smaller model, fewer steps), which cannot grade a published number. We ran the paper's own configuration and graded its actual numbers. Our method is a one-factor-at-a-time ablation whose factors come from the settings diff, the idea behind delta debugging and git bisect applied to experiment settings; the contribution is wiring it to the diff and the verdicts so every flagged difference is tested.

Build plan

The extraction steps have had a blind test. The three agentic steps that make this an automated auditor have not, so they come first, each with a test, and the grader rules were fixed before any UI.

OrderStepTest that says it works
1Repair agent: classify each patch as environment, compatibility or hypothesis, then run the inertness checkon MatchDG it must reproduce our three repair commits and send the missing target domain to a branch
2Claim-to-command linker: turn "Table 1, PerfMatch" into a runnable commandon MatchDG it must produce the commands we wrote by hand for all 9 Table 1 rows and all 24 Table 11 cells
3Branch-patch writer: one commit per findingself-check on every branch: re-run the code extractor and require that exactly one setting changed, the one the finding names
4Code extractor on a data-pipeline question, with schema version 2 (adds resizing, normalisation, augmentation, domain construction and the data the selection metric reads)on robustdg it must trace SciCoQA row 67 to the path we traced by hand for F7
5Second paper, end to end, blind (first milestone)two CPU-runnable papers with a SciCoQA row or an MLRC report, run before any UI; the known discrepancy is read only after the run. The run also measures wall-clock time and tokens per paper
6Regression: MatchDG as golden outputsevery pipeline change re-derives all MatchDG verdicts exactly (scripts/regression.py)
7Report UI and demothe report screen exists (this page); add submit and job status. Demo is precomputed, plus one live run
